### 阶段 2：DRL 语法进阶（LHS 条件）

- Pattern 匹配与字段约束

`and`和`&&`的区别：

and只能出现在条件与条件之间，&&只能出现在字段之间。

```.drools
// ✅ 写法1：换行（什么都不写，默认就是 and）—— 最常用
exists Order(user == $u)
not Order(user == $u, refunded == false)

// ✅ 写法2：显式写 and —— 也合法（我已实测跑通）
exists Order(user == $u) and not Order(user == $u, refunded == false)

// ❌ 写法3：用 && —— 报错，因为 && 连接不了条件元素
exists Order(user == $u) && not Order(user == $u, refunded == false)
```

一句话总结：`括号内`用符号（`&&`、`||`），`括号外`用单词（`and`、`or`、`not`、`exists`）

### 阶段 3：RHS 动作与事实变更

- insert / modify / update / delete(retract)
- 规则属性：salience / no-loop / lock-on-active / agenda-group / activation-group / date-effective / enabled
- 理解并规避无限循环
- ✅ 产出：掌握规则执行顺序控制

<strong> ① salience —— 优先级（解决你练习1的"规则冲突"）</strong>

salience 就是解药——数值越大，越先执行（默认是 0）：

```.drools

rule "大额VIP打8折"
    salience 100          // 优先级最高，先执行
    when
        $o : Order( amount > 1000, user.level == "VIP" )
    then
        $o.setDiscount(0.8);
        update($o);
end

rule "普通折扣9折"
    salience 0            // 低优先级，后执行
    when
        $o : Order( amount >= 500 )
    then
        $o.setDiscount(0.9);
        update($o);
end
```
现在即使两条都命中，也是 8 折规则先跑。但这里还有个坑要提醒你：后执行的 9 折规则仍然会覆盖 8 折。所以真正要"互斥、只跑一个"，光靠 salience 还不够，得配合下面的 activation-group 或给规则加互斥条件。

salience 小结：只决定"先后顺序"，不决定"跑不跑"。它解决的是"顺序问题"，不是"互斥问题"。

<strong> ② activation-group —— 激活组（互斥，一组只跑一个）</strong>
这是解决"互斥"的正解。同一个 activation-group 里的多条规则，只要有一条触发，其余的全部取消。

```.drools

rule "VIP打8折"
    activation-group "discount"     // 组名
    when
        $o : Order( user.level == "VIP" )
    then
        $o.setDiscount(0.8);
        update($o);
end

rule "普通用户打9折"
    activation-group "discount"     // 同一组
    when
        $o : Order( user.level == "普通" )
    then
        $o.setDiscount(0.9);
        update($o);
end
```
同一个订单，VIP 和普通只能命中一条，本来就不会同时满足。activation-group 真正威力在一个订单命中多条同组规则时——比如按金额分档的折扣，它保证只取一个档位。这就是典型"规则互斥"场景的解法。

记住区别：salience 是"排序"（大家都跑，谁先谁后）；activation-group 是"互斥"（只跑一个，其余作废）。

<strong> ③ agenda-group —— 议程组（分组 + 焦点控制）</strong>
这个最特殊，它让你能把规则分成不同的"执行阶段"，用代码控制先执行哪一组。

关键：只有"获得焦点（focus）"的 agenda-group 里的规则才会执行，其他组的规则即使匹配了也按兵不动。

```.drools

rule "风控检查规则"
    agenda-group "risk"      // 属于 risk 组
    when
        $o : Order( amount > 100000 )
    then
        $o.setBlocked(true);
        update($o);
end

rule "正常下单规则"
    agenda-group "checkout"  // 属于 checkout 组
    when
        $o : Order()
    then
        System.out.println("订单通过：" + $o.getId());
end
```

Java 代码里这样控制执行顺序：

```.java

    KieSession session = kc.newKieSession();
    session.insert(order);
    
    // 先执行风控组（只跑 risk 组的规则）
    session.getAgenda().getAgendaGroup("risk").setFocus();
    session.fireAllRules();
    
    // 再执行下单组
    session.getAgenda().getAgendaGroup("checkout").setFocus();
    session.fireAllRules();
```
这就是规则流的雏形——把规则按业务阶段编排："先风控，后下单"，代码完全掌控执行节奏。

- `no-loop`：禁止规则因自己的 update 再次触发自己。
- `lock-on-active`：no-loop 的加强版，当规则在某个 ruleflow-group/agenda-group 中激活后，禁止它再被其他规则激活。防"规则A→B→A"的环。用得少，了解即可。
- `date-effective` / `date-expires`：规则在某个日期后生效 / 某日期后失效。用于"活动规则到点自动下线"。
- `enabled`：布尔开关，enabled false 时规则完全不参与匹配。用于临时停用某条规则。

agenda-group和ruleflow-group的区别：
- agenda-group：靠代码 setFocus() 手动激活。
- ruleflow-group：本意是配合 jBPM 规则流（RuleFlow）自动激活，单独用 getAgendaGroup 去控制它是"借用"行为，在复杂场景下可能不按预期工作。

## ① global —— 全局变量（跨规则共享，但只能读）

 `global`。它和 `$m` 的区别：

- `$m`：规则内局部绑定变量，各自独立。
- `global`：整个会话共享的对象，所有规则都能访问。

**声明**（DRL 里）：

```drl
global java.util.List resultList   // 声明一个全局 List
```

**注入**（Java 代码里，在 fire 之前设置）：

```java
    List<String> resultList = new ArrayList<>();
    session.setGlobal("resultList", resultList);   // 名字要和 DRL 里一致
    session.fireAllRules();
    // 规则执行后，resultList 里就有结果了
```

**使用**（规则里）：

```drl
rule "记录大额订单"
    when
        $o : Order( amount > 10000 )
    then
        resultList.add($o.getId());   // 往全局 List 里加数据
end
```

⚠️ **关键铁律：`global` 在规则里只能"用"，不能"改"**。意思是：你可以调用 `resultList.add(...)`（改变 List 的内容），但**不能写 `resultList = new ArrayList()`**（重新赋值）。因为 global 是会话级共享的引用，规则里改了引用会导致结果不一致。

**典型用途**：规则执行后，把结果收集到 global 的 List/Map 里，供 Java 代码读取。这是"规则产出结果"的标准做法。

## ② query —— 查询（从工作内存查数据，但不改任何东西）

规则（rule）会"动作"，查询（query）只"查数据"，是纯只读的。它相当于一个"预定义的筛选条件"，Java 代码可以反复调用，取出符合条件的事实。

```drl
query "大额订单查询" $o    // 查询名 + 参数（要返回的变量）
    $o : Order( amount > 10000 )
end
```

Java 代码调用：

```java
    QueryResults results = session.getQueryResults("大额订单查询");
    for (QueryResultsRow row : results) {
        Order o = (Order) row.get("$o");   // 取出查询结果
        System.out.println(o.getId());
    }
```

**和规则的区别**：规则是"匹配到就执行 then 动作"，query 是"匹配到就返回结果"，**不会触发任何动作、不会改变工作内存**。适合"查一下现在有哪些事实符合条件"的场景。

## ③ function —— 函数（封装可复用的计算逻辑）

`function` 让你在 DRL 里定义一个可复用的函数，规则里可以调用它，避免重复代码：

```drl
function double calcDiscount(double amount) {
    if (amount > 10000) return 0.6;
    if (amount > 5000) return 0.8;
    return 0.9;
}

rule "打折"
    when
        $o : Order()
    then
        $o.setDiscount( calcDiscount($o.getAmount()) );   // 调用函数
        update($o);
end
```

**注意**：`function` 里写的是标准 Java 代码。不过实际项目中，复杂逻辑更推荐写在 Java 类里用静态方法调用，而不是堆在 DRL 里。`function` 适合放一些轻量、和规则强相关的小工具函数。

## 三块小结

| 特性 | 作用 | 关键点 |
|------|------|--------|
| `global` | 跨规则共享变量 | 规则里只能"用"不能"改引用" |
| `query` | 只读查询 | 不触发动作，Java 用 `getQueryResults` |
| `function` | 封装复用逻辑 | 轻量工具函数，复杂逻辑放 Java |

这三个的共同点是：**它们让 DRL 从"纯规则"扩展成一个更完整的规则编程环境**——能共享数据（global）、能查数据（query）、能复用代码（function）。
